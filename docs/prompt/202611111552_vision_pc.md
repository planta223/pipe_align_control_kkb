# 비전 PC Codex 인수인계

이 저장소는 Control PC에서 개발한 `pipe_align_control_kkb`를 비전 PC에 clone한 것이다. 아래 맥락을 유지하여 **비전 PC에서 pose 발행·통신 상태를 조사하고 제어 PC 담당자에게 결과를 전달하라.** 제어 PC 자체의 진단은 제어 PC 담당 Codex가 수행한다.

먼저 `README.md`, `main/vision_pc/README.md`, `docs/preliminary_work/README_vision_pc.md`, `.gitignore`를 읽어라. 과거 인수인계보다 현재 실행 중인 프로세스·설정·실제 메시지를 우선한다.

## 목표와 현재 상태

- 목표는 FoundationPose의 두 Pipe pose를 제어 PC에서 받아 Dual xArm 미세 정렬로 연결하는 것이다.
- 양팔은 Pipe를 잡고 `pre_align_ready` 자세에 도달한 상태다. 준비 이동은 실물에서 동작 확인됐으며, 지금은 로봇을 다시 움직일 단계가 아니다.
- 사용자는 비전도 발행 중일 것으로 예상하지만, 비전 PC의 실제 발행 여부는 아직 확인하지 못했다.
- **기존 공유기가 새 공유기로 교체됐다.** 이전 IP·서브넷·SSID·멀티캐스트 정책이 그대로라고 가정하지 않는다.
- 이번 작업은 비전 PC의 발행 상태와 제어 PC 방향 통신에 필요한 정보를 조사하는 것이다. 정렬 제어 구현·속도 조정·좌표계 보정은 이번 범위가 아니다.

## 제어 PC에서 확인한 사실

아래는 2026-11-11 조사 시점의 정보다. 비전 PC 담당자에게 제공하는 참고 정보이며, 제어 PC에서 실행할 진단 절차를 작성하거나 직접 수행할 필요는 없다.

| 항목 | 확인 내용 |
|---|---|
| 제어 PC ROS 환경 | Humble, `rmw_fastrtps_cpp`, `ROS_DOMAIN_ID=8`, `ROS_LOCALHOST_ONLY=0`으로 확인 |
| 제어 PC Wi-Fi | `wlo1`, `10.102.101.110/24` |
| 제어 PC 기본 게이트웨이 | `10.102.101.1`, `wlo1` |
| 제어 PC 로봇용 유선망 | `enp86s0`, `192.168.2.8/24` |
| 과거 제어 PC Wi-Fi 주소 | `192.168.10.104/24`; 현재 주소로 사용하지 않음 |
| 제어 PC 수신 조사 | 좌우 pose를 8초간 구독했으나 양쪽 publisher 0개, 수신 0건 |
| 같은 조사에서 발견된 노드 | RoHand·selector 노드는 발견됐으나 외부 카메라 publisher는 미발견 |

현재 결과는 제어 PC에서 비전 publisher를 발견하지 못했다는 뜻이다. 비전 PC 자체가 발행하지 않는 것인지, PC 간 discovery/통신이 막힌 것인지는 아직 구분되지 않았다. Wi-Fi 주소는 DHCP로 바뀔 수 있으므로 필요하면 제어 PC 담당자에게 최신 주소를 요청하라. 로봇용 유선 주소를 PC 간 통신 주소로 대신 사용하지 마라.

## 기존 비전 실행 환경

기존 문서상 환경은 다음과 같다. 실제 경로·프로세스와 일치하는지 현지에서 확인하라.

- 카메라: `~/Pipe_Align_kkb/ZED2i_ROS/cam_zed.py`, 비전 호스트 Humble + conda `zed_cam`.
- 추적: `~/Pipe_Align_kkb/MULTI_OBJECT_TRACKING/scripts/test_multi_object.py`.
- FoundationPose: 기존 Docker 컨테이너 `foundationpose`, ROS2 Foxy + `/opt/conda/envs/my/bin/python`.
- 기존 컨테이너 설정: host network, `/home` mount. 실제 `docker inspect` 결과로 재확인한다.
- 기존 tracker의 DDS XML: `/home/rico/Pipe_Align_kkb/MULTI_OBJECT_TRACKING/ros2/fastdds_udp.xml`.
- `main/vision_pc/src/temp_adaptor/`의 YAML은 참조 기록이며 현재 실행에 적용되는 설정으로 간주하지 않는다.

호스트에는 Humble, 컨테이너에는 Foxy 환경을 사용한다. 새 터미널의 환경과 실제 실행 중인 카메라·tracker의 환경을 구분하라. 새 창에서 `export`해도 기존 프로세스 환경은 바뀌지 않는다.

## 이번 비전 PC 작업

1. **현재 실행 상태를 확인하라.** 카메라·tracker의 실제 PID, 실행 파일·인자, 환경, 컨테이너 상태와 network mode를 확인한다. 카메라만 실행 중인지, 초기 mask 확인/등록 대기인지, tracking 진행 중인지, 오류로 멈췄는지 구분한다. 기존 프로그램을 중복 실행하지 않는다.
2. **카메라 입력을 확인하라.** 컬러·깊이·camera_info publisher와 실제 메시지 갱신, tracker의 영상 수신 여부를 확인한다. 입력이 끊겼다면 그 지점과 로그를 보고한다. 기본 카메라 15 FPS를 실제 pose 발행 주기로 대신 기록하지 않는다.
3. **컨테이너 안의 좌우 pose를 확인하라.** 양쪽 publisher/node/type/QoS와 실제 메시지 수신을 각각 확인한다. publisher는 있는데 메시지가 없으면 발행 조건·초기 등록·tracking lost·예외 로그를 조사한다.
4. **비전 호스트의 좌우 pose를 확인하라.** 컨테이너 안과 같은 결과인지 비교한다. 컨테이너 안 성공·호스트 실패라면 container/network/transport 설정부터 조사한다. 로컬 수신 성공을 제어 PC 수신 성공으로 보고하지 않는다.
5. **새 공유기 관련 정보를 확인하라.** 비전 PC의 현재 NIC·IP/프리픽스·SSID·게이트웨이, 제어 PC IP로 가는 실제 `dev`·`src`, ping 결과를 기록한다. 게스트망·단말 격리·유무선 격리·VLAN·멀티캐스트 필터 정책은 확인 가능한 사실만 보고한다. 같은 SSID만으로 PC 간 통신 가능하다고 단정하지 않는다.
6. **실제 publisher의 DDS 설정을 조사하라.** Domain/RMW/localhost, 적용 XML, Discovery Server, NIC 제한·광고 주소를 확인한다. 과거 `192.168.10.*` IP나 이전 NIC 이름이 고정돼 있는지, UDP 대신 공유 메모리에만 의존하는지 조사한다. 의도한 설정 파일과 프로세스가 실제 사용하는 설정을 구분한다.
7. **비전 PC에서 가능한 통신 증거를 모아라.** 필요하면 제어 PC 담당자와 시간을 맞춰 비전 호스트에서 `ros2 multicast send/receive` 또는 `/communication_debug/*` 문자열 토픽 송수신을 수행한다. 반대쪽 대기가 필요한 시험은 먼저 조율하고, 비전 PC 단독 시험을 양 PC 간 성공으로 간주하지 않는다. 제어 PC 명령 실행·설정 변경은 제어 PC 담당자에게 맡긴다.
8. **다음 연동에 필요한 출력 정보를 보고하라.** 실제 pose 샘플, 수신 창 길이·건수·주기·끊김, 좌우 대응, stamp 갱신과 시계 동기화 상태를 정리한다. 카메라 변환 미측정이나 시간 오차만으로 publisher 0개를 설명하지 않는다.

## 비전 PC에서 사용할 확인 명령

아래 명령은 비전 PC에서만 실행한다. 실행 중 프로세스의 시작 터미널·로그와 환경도 별도로 확인하라. 전체 환경변수를 출력하지 말고 ROS·DDS 관련 항목만 기록하라.

비전 호스트의 네트워크·실행 상태:

```bash
hostname
date --iso-8601=seconds
ip -brief address
ip route
nmcli -f NAME,TYPE,DEVICE connection show --active
ip route get 10.102.101.110
ping -c 4 -W 1 10.102.101.110
printenv ROS_DOMAIN_ID ROS_LOCALHOST_ONLY RMW_IMPLEMENTATION FASTRTPS_DEFAULT_PROFILES_FILE FASTDDS_DEFAULT_PROFILES_FILE ROS_DISCOVERY_SERVER
docker ps -a --filter name=foundationpose
docker inspect --format '{{.State.Status}} {{.HostConfig.NetworkMode}}' foundationpose
pgrep -af 'cam_zed.py|test_multi_object.py'
```

제어 PC IP는 위 조사 시점 값이다. 변경됐다면 최신 주소로 바꿔 확인한다. `nmcli`가 없으면 IP·라우팅과 실제 SSID를 기록하라. ping 실패는 ICMP 차단일 수 있고, 성공해도 DDS 통신을 보증하지 않는다.

비전 **호스트의 새 확인용 터미널**:

```bash
source /opt/ros/humble/setup.bash
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_DOMAIN_ID=8
export ROS_LOCALHOST_ONLY=0
ros2 topic info --no-daemon --spin-time 3 -v /cam/color/compressed
ros2 topic info --no-daemon --spin-time 3 -v /cam/depth/compressed
ros2 topic info --no-daemon --spin-time 3 -v /cam/color/camera_info
ros2 topic info --no-daemon --spin-time 3 -v /vision/left_pipe/pose
ros2 topic info --no-daemon --spin-time 3 -v /vision/right_pipe/pose
timeout 10s ros2 topic echo --once /vision/left_pipe/pose geometry_msgs/msg/PoseStamped --qos-reliability best_effort
timeout 10s ros2 topic echo --once /vision/right_pipe/pose geometry_msgs/msg/PoseStamped --qos-reliability best_effort
```

컨테이너가 이미 running이면 `docker exec -it foundationpose bash`로 별도 확인용 터미널을 연다. **컨테이너 안**에서는 `/opt/ros/foxy/setup.bash`를 source하고 기존 tracker와 동일한 Domain/RMW/XML 조건에서 같은 두 pose의 publisher와 실제 수신을 확인하라. 호스트의 Humble 환경을 컨테이너에 적용하지 않는다. XML 경로가 없으면 임의로 대체 파일을 만들지 말고 그 사실을 보고한다.

토픽 목록은 구독자만 있어도 이름이 나타날 수 있다. publisher 수와 실제 pose 도착을 따로 확인한다. `--once`가 출력 없이 timeout되면 성공이 아니다. CLI cache 영향을 피하는 `--no-daemon`은 호스트의 확인 명령에 사용하며, 컨테이너 CLI 옵션은 해당 Foxy 설치에서 지원 여부를 확인한다.

## 현재 문서상 pose 계약

현지 소스와 실제 메시지로 아래 계약을 재확인하고, 달라진 부분은 정확히 보고하라.

| 항목 | 기대값 |
|---|---|
| 좌우 토픽 | `/vision/left_pipe/pose`, `/vision/right_pipe/pose` |
| 타입 | `geometry_msgs/msg/PoseStamped` |
| 좌표계 | `camera_left_optical_frame`, Pipe CAD 기준 `C_T_P` |
| 단위·회전 | 위치 m, quaternion `x,y,z,w` |
| QoS | BEST_EFFORT / VOLATILE / depth 1 |
| timestamp | 입력 영상 stamp 유지; 동일 영상의 좌우 결과는 같은 stamp |
| 추적 실패 | 해당 객체 pose 중단; 별도 tracking status 토픽 없음 |
| 좌우 배정 | `--left-pipe-object-id pipe1`이면 pipe1이 left, 나머지가 right |

기존 실행 예시는 `--z-axis-stabilization`을 사용해 Z축 주위 회전을 제거한다. 현재 실제 실행 옵션도 같은지 보고하라. 과거 인수인계의 tracking status 토픽·고정 15 Hz 설명을 현재 계약으로 되살리지 않는다.

## 제어 PC에 전달할 결과

다음 순서로 **확인 사실 / 추정 원인 / 미확인**을 구분하여 보고하라.

1. 비전 PC의 현재 NIC·IP/프리픽스·SSID·게이트웨이와 제어 PC 방향 경로·ping 결과.
2. 카메라·tracker의 실제 실행 상태, 명령·환경·컨테이너 network mode 및 적용 DDS XML.
3. 카메라 입력 상태와 컨테이너/호스트 각각의 좌우 publisher 수·실제 pose 수신 결과.
4. 실제 pose 한 건씩, frame·stamp·QoS·좌우 대응·관측 주기·끊김.
5. 실패가 시작되는 최초 지점과 직접 근거가 되는 파일·함수·오류 로그.
6. 이전 공유기 주소·NIC 고정이나 격리 정책을 발견했다면 정확한 항목과 현재 값.
7. 제어 PC 담당자가 이어서 확인해야 할 비전 측 송신 조건·시험 시간·남은 질문.
8. 변경이 필요하다면 대상·이유·변경 전후 값·되돌리는 방법을 제안한다. 이번 진단에서 임의 적용하지 않는다.

비전 호스트에서도 pose가 안 나오면 그 원인부터 보고하라. 호스트에서는 정상인데 제어 PC 방향만 미확인이면, 그 경계를 명확히 하여 제어 PC 담당자가 네트워크 진단을 이어갈 수 있게 하라.

## 작업 제한

- 기존 비전 소스·가상환경·Docker·공유기·방화벽·시스템 설정을 보존한다. 재설치, 컨테이너 재생성, `.bashrc` 변경, 기존 프로세스 임의 종료를 하지 않는다.
- `FoundationPose/docker/run_container.sh`는 기존 컨테이너를 삭제할 수 있으므로 실행하지 않는다.
- 로봇·손 motion command, 실제 vision pose 토픽으로의 가짜 pose 발행, pre_align 재실행은 하지 않는다.
- 양 PC 통신 시험은 `/communication_debug/*` 문자열 토픽이나 multicast 시험만 사용한다. 제어 PC 로컬 진단은 제어 PC 담당자가 수행한다.
- 인증정보·비밀번호·라이선스 키를 출력하지 않는다. Git 전역 설정 변경과 임의 commit/push는 하지 않는다.
- 실행하지 않은 항목을 성공했다고 보고하지 않는다. 통신 수신 성공과 pose 정확도·로봇 정렬 성공을 구분한다.

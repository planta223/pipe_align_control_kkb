# 비전 PC Codex 인수인계

이 저장소는 Control PC에서 개발한 `pipe_align_control_kkb`를 비전 PC에 clone한 것이다. 아래 맥락을 유지하여 **현재 pose의 좌표 의미·왼쪽 추적 불안정·실물 좌우 대응을 비전 PC에서 조사하고 제어 PC 담당자에게 전달하라.** 제어 PC의 수신 검사와 `vision_ready` 구현은 제어 PC 담당 Codex가 수행한다.

먼저 `README.md`, `main/vision_pc/README.md`, `docs/preliminary_work/README_vision_pc.md`, `.gitignore`를 읽어라. 기존 `docs/prompt/202611111552_vision_pc.md`는 통신 장애를 조사하던 시점의 기록이며, 이번 작업은 아래의 갱신된 현재 상태를 기준으로 한다.

## 목표와 현재 상태

- 목표는 FoundationPose의 두 Pipe pose를 받아 Dual xArm 미세 정렬로 연결하는 것이다.
- 양팔은 Pipe를 잡고 `pre_align_ready` 자세에 도달했다. 이번에는 로봇·손을 움직이거나 준비 자세를 다시 만들지 않는다.
- 공유기 교체 후 통신을 조사했으나, 사용자는 **랜선 미연결이 원인이었다고 확인했다. 연결 후 제어 PC에서 양쪽 pose 수신이 실제로 확인됐다.** 현재 문제를 publisher 0개 상태로 되돌려 진단하지 않는다. 새 장애가 관측되면 별도로 기록한다.
- 현재 필요한 것은 수신 자체가 아니라 **발행된 좌표의 정확한 의미와 정지 상태의 pose 안정성 검증**이다.
- 사용자는 아래 수집 구간에 양팔·파이프·카메라를 모두 그대로 유지했다고 확인했다. 가림·너무 가까운 거리·FoundationPose 특성은 사용자 추정이며 원인으로 확정하지 않았다.

## 이번 비전 PC 작업

### 1. 실제 pose 발행 코드와 좌표 계약 확인

실행 중 tracker의 PID·시작 인자·실제 import 경로부터 확인하고, 추정 결과가 `PoseStamped`로 바뀌는 흐름을 함수 단위로 추적하라.

- raw 추정 변환이 무엇을 의미하는지, 최종 발행값이 정말 `C_T_P`인지 확인한다. `A_T_B`는 B 좌표를 A로 옮기는 변환이다.
- C는 정확히 어느 카메라의 optical frame인지, 축 방향과 원점은 무엇인지 확인한다. `frame_id` 문자열만으로 좌표 기준이 검증됐다고 보고하지 않는다.
- P는 원본 CAD 원점인지, mesh 정규화/중심화 뒤 원점인지, bbox/표시용 원점인지 구분한다. CAD 단위·원점·주축·길이 범위와 내부 변환의 적용/역변환을 확인한다.
- 원본 추정 → 후처리 → 좌표 변환 → ROS 발행 순서와 행렬 곱 순서를 정리한다. 단위 변환, 축 반전·교환, 원점 이동, 회전 제거가 어디에 적용되는지 확인한다.
- `--z-axis-stabilization` 및 symmetry 관련 처리가 실제 활성화됐는지, 출력의 어떤 회전 자유도를 제거/변경하는지 확인한다. 위치에도 영향을 주는지 소스로 확인한다.
- 영상에 그리는 CAD·축과 ROS로 발행하는 pose가 같은 변환인지 확인한다. 표시가 정상이어도 발행 좌표가 별도로 가공될 수 있으므로 실제 호출 인자를 대조한다.
- source 영상 stamp, 실제 추정에 사용한 프레임, ROS 발행 stamp의 연결을 확인한다. 약 15 Hz 수신만으로 추론도 매 프레임 새로 수행된다고 단정하지 않는다. 이전 추정값 재사용·주기 발행·비동기 처리 여부를 확인한다.

결과는 코드 경로·함수·행 번호와 변환식으로 보고하라. 출력값만 보고 좌표 기준을 추측하지 않는다.

### 2. 왼쪽 추적 불안정의 관측 증거 수집

현재 로봇·파이프·카메라를 유지한 상태의 기존 영상·추적 화면·로그를 우선 확인하라. 가림이나 근거리가 원인이라고 가정하고 시작하지 않는다.

- 왼쪽 Pipe의 가림 정도, 화면 경계 잘림, 추적 CAD·축의 튐, 초기 등록 적합성을 오른쪽과 비교한다.
- YOLO mask가 초기 등록에만 쓰이는지, tracking 중 갱신되는지 확인한다. 초기 mask와 현재 물체 위치를 혼동하지 않는다.
- 실제 사용 중인 깊이 설정·최소 거리·유효 범위를 코드와 실행 조건에서 확인한다. 왼쪽 Pipe 영역의 유효/무효 깊이 비율과 대표 깊이, 깊이 튐·결측을 가능한 범위에서 조사한다. ZED 모델명만 보고 최소 거리를 임의로 단정하지 않는다.
- RGB·depth·mask 해상도와 정렬 관계, K의 스케일 적용, 이미지/깊이 stamp 짝이 맞는지 확인한다.
- 추정 원본과 후처리·ROS 출력 중 어느 단계에서 큰 변화가 생기는지 확인한다. 위치·축 변화와 입력 깊이/추적 상태를 같은 시간·프레임 기준으로 비교한다.
- CAD 원점이 물체에서 떨어져 있어 작은 회전이 큰 원점 위치 변화로 나타나는지, 대칭성·다중 해·깊이 입력 문제인지 구분한다. 확인되지 않으면 미확인으로 남긴다.
- 재등록·lost·오래된 pose 재사용·새 stamp 부여 조건을 확인한다. 명시적 tracking status 토픽이 없더라도 내부 유효성 신호가 있는지 조사한다.

새로운 ZED 장치 세션이나 tracker를 중복 실행하지 않는다. 필요하면 기존 ROS 영상의 읽기 전용 구독으로 조사한다. 과거 16:11:50 구간 영상이 없다면 새 관측 구간임을 명시하고, 과거 CSV와 정확히 동기화됐다고 주장하지 않는다.

이번에는 필터·평균·마스크·등록 옵션을 변경해 증상을 숨기지 않는다. 변경이 필요하면 관측 근거와 별도 제안을 먼저 정리한다. 정지 상태의 반복성은 절대 정확도와 구분한다.

### 3. left/right와 실제 잡은 팔의 대응 확인

- 현재 `pipe1`/`pipe2`가 어떤 초기 mask에 배정됐고 `--left-pipe-object-id`가 실제로 무엇인지 확인한다.
- 영상 왼쪽을 로봇 왼팔이라고 가정하지 않는다. 현재 추적 ID → ROS 토픽 → 실제 잡은 팔의 대응을 명시한다.
- 추적 중 영상 위치가 바뀌었을 때 재정렬·ID 교환이 일어나는 경로가 있는지 확인한다.
- 화면과 코드만으로 실물 대응을 확정할 수 없으면 사용자에게 필요한 최소 확인 사항을 요청한다. 확인을 위해 로봇을 임의로 움직이지 않는다.

## 작업 제한

- 기존 비전 소스·가상환경·Docker·시스템 설정을 보존한다. 우선 읽기 전용으로 조사하며, 재설치·컨테이너 재생성·`.bashrc` 변경·기존 프로세스 임의 종료를 하지 않는다.
- `FoundationPose/docker/run_container.sh`는 기존 컨테이너를 삭제할 수 있으므로 실행하지 않는다.
- 로봇·손 motion command, 실제 vision pose 토픽으로의 가짜 pose 발행, pre_align 재실행을 하지 않는다. 카메라나 파이프 위치도 임의로 바꾸지 않는다.
- 카메라→로봇 calibration은 별도 미완료 과제다. 제어 PC의 base 기울기 보정을 카메라 calibration으로 간주하지 않는다. raw 카메라 pose의 흔들림을 제어 PC 장착 회전값 때문이라고 추정하지 않는다.
- 수집 로그·이미지·CSV는 비전 PC의 `main/vision_pc/_log/` 아래에 저장하고 원본 소스나 저장소 루트에 산출물을 만들지 않는다. 실행 중 원본 프로그램의 기존 로그 경로를 임의 변경하지 않는다.
- 인증정보·비밀번호·라이선스 키를 출력하지 않는다. Git 전역 설정 변경과 임의 commit/push는 하지 않는다.
- 실행하지 않은 항목을 성공했다고 보고하지 않는다. 통신 정상·pose 반복성·좌표 의미·절대 정확도·실물 정렬 성공을 각각 구분한다.
